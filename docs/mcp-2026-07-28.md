# MCP protocolVersion 2026-07-28

This implementation supports only the stateless MCP Streamable HTTP revision
`2026-07-28`. Earlier protocol revisions and their session-based lifecycle are
not supported.

For the 2026-07-28 path, every POST must include all of the following:

- `MCP-Protocol-Version: 2026-07-28`
- `Mcp-Method`, equal to the JSON-RPC `method`
- `Mcp-Name` for `tools/call`, `resources/read`, and Task methods, equal to
  `params.name`, `params.uri`, or `params.taskId`, respectively
- `params._meta.io.modelcontextprotocol/protocolVersion`
- `params._meta.io.modelcontextprotocol/clientCapabilities`

The protocol version in the HTTP header and request `_meta` must be identical.
The server returns JSON-RPC error `-32020` for mismatched request headers and
`-32022` for an unsupported protocol version.

`initialize`, `notifications/initialized`, HTTP GET/DELETE, and the
`Mcp-Session-Id` header are not supported. An APEX session is created only for
the duration of each request and is never sent to the client. Where RAS is
configured, the RAS session has the same request lifetime.

## Browser origins

Requests without an `Origin` header are accepted for native MCP clients. If a
request has an `Origin` header, its exact serialized origin must be present in
`OJ_MCP_ALLOWED_ORIGINS`; otherwise the server returns HTTP 403. The table is
empty after installation, so browser access is denied by default. For example,
allow a locally hosted client with:

```sql
insert into oj_mcp_allowed_origins(origin)
values ('http://127.0.0.1:8181');
commit;
```

Store only trusted origins and include the non-default port when applicable.

Use `server/discover` to obtain the server capability set and supported
versions:

```http
POST /ords/<schema>/<module>/mcp HTTP/1.1
Content-Type: application/json
MCP-Protocol-Version: 2026-07-28
Mcp-Method: server/discover

{"jsonrpc":"2.0","id":1,"method":"server/discover","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}}}}
```

Successful results include `resultType: "complete"` and server identity in
`_meta.io.modelcontextprotocol/serverInfo`. Discovery and the list/read
methods include the required `ttlMs` and `cacheScope` cache metadata. The
server does not advertise change notifications because it does not implement
the `subscriptions/listen` stream.

## Tasks extension

The server advertises `io.modelcontextprotocol/tasks` from `server/discover`.
Task augmentation currently applies only to `tools/call`, as required by the
extension. A client opts in on each request by including:

```json
{
  "_meta": {
    "io.modelcontextprotocol/clientCapabilities": {
      "extensions": {
        "io.modelcontextprotocol/tasks": {}
      }
    }
  }
}
```

When both the client capability and the tool's Task configuration are present,
`tools/call` returns a durable `CreateTaskResult` with `resultType: "task"`.
Oracle Advanced Queuing executes the tool in the background, and the client
polls `tasks/get` until the status becomes `completed`, `failed`, or
`cancelled`. The server also implements the empty acknowledgements for
`tasks/update` and `tasks/cancel`.
Task IDs contain 256 bits generated by `DBMS_CRYPTO.RANDOMBYTES` and are scoped
to the authenticated MCP caller.

The database execution schema is captured with the Task. AQ notification
callbacks may run in an Oracle background session whose `SESSION_USER` is
`SYS`; the captured schema ensures UC_AI placeholders such as
`#SESSION_USER#` still resolve to the schema that accepted the original MCP
request.

All `tasks/get`, `tasks/update`, and `tasks/cancel` requests must declare the
Tasks capability and send `Mcp-Name: <taskId>`. A missing Tasks capability
returns JSON-RPC error `-32003`; an invalid, expired, or inaccessible task ID
returns `-32602`.

Task execution is opt-in per tool. Configure it in `OJ_MCP_TOOLS_EXTRAS`:

```sql
update oj_mcp_tools_extras
   set task_enabled = 1,
       task_ttl_ms = 3600000,
       task_poll_interval_ms = 1000
 where tool_id = (select id from uc_ai_tools where code = 'run_sql');
commit;
```

`task_ttl_ms = NULL` means that the Task has no server-declared expiry.
`task_poll_interval_ms` is the suggested polling interval. The sample
`run_sql` tool is Task-enabled by `src/tools/register_tools.sql`.

This implementation uses polling and does not implement optional
`notifications/tasks` delivery. Its tools do not generate in-task client
requests, so no Task enters `input_required`; `tasks/update` still validates
the request and acknowledges unknown response keys as required by the
extension.
